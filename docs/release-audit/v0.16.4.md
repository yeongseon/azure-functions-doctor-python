# v0.16.4 tag investigation

Status: **read-only investigation (issue #670)**. Nothing was moved, deleted or edited. Evidence was
gathered on 2026-11-13 from `git ls-remote --tags`, `git`, `gh release view`, `gh run list`, the GitHub
compare API and the PyPI JSON API (`https://pypi.org/pypi/azure-functions-doctor/json`).

## Verdict

`v0.16.4` is **not a valid package release**. It is a Git tag plus a GitHub Release record with no
PyPI distribution, and it must not be treated as an installable version.

## How it happened (what can and cannot be proven)

- At the tag, `.github/workflows/create-release.yml` created a GitHub Release for **every** `v*` tag
  push, independently of `publish-pypi.yml`. A failed publish therefore still left a normal-looking
  Release. This is the mechanism behind the misleading metadata, and it is verified from the workflow
  file at the tagged commit and the run conclusions above.
- The tagged commit declares `0.16.2`, and `publish-pypi.yml` at that commit contains a
  tag-versus-`__version__` check. The publish run failed after 8 s, which is consistent with that check
  rejecting `0.16.4 != 0.16.2`. **The job log is no longer retrievable (HTTP 410), so the exact failing
  step is not directly verified.**
- The commit was created on a branch started from the v0.16.2-era history and was tagged without being
  merged into `main`. Who pushed the tag and from which local branch is not recoverable from the
  remaining data.
- Release Please was not in the path (no release PR, no changelog entry). Since then the Release Please
  flow owns tags and Releases; see [Release Process](../release_process.md).

## Impact assessment

- Users: `pip install azure-functions-doctor==0.16.4` fails (no such version); the Release page can
  mislead. No code path in this repository refers to the version.
- Not verified: references to `v0.16.4` in other repositories or external documentation.

## Proposed corrective steps (none executed; owner action)

1. **Keep the tag.** Do not move, delete or re-point it, and do not create a different commit as
   `0.16.4` (audit history and "no force-move of tags" constraint in #670). The next valid version is
   whatever Release Please cuts from `main` (versions after `0.16.3` already published: `0.17.0`...`0.23.1`).
2. **Annotate the GitHub Release body** (edit only the Release notes; tag and artifacts untouched) with
   a top-of-page notice, for example:

   > **Not a published package release.** Tag `v0.16.4` points at commit `2e45245` that declares
   > `0.16.2` and is not on `main`. The PyPI publication failed and no `0.16.4` distribution exists.
   > Use `0.16.3` or later (`0.17.0`+). Retained for audit history.

   Optionally mark the Release as a **pre-release** so it is not shown as "Latest"-grade; this does not
   alter the tag. Use `tools/release_notes.py` conventions (see #657) for layout.
3. **Prevent recurrence** (implemented separately in #672): reject tags whose source version differs or
   that are not on `main` before any candidate is built, and keep the registered exception for this tag
   pinned to commit `2e45245f3f39`. Release creation is now owned by Release Please, not by a per-tag
   workflow that ignores publish outcome.
4. Re-check external references (sibling repositories, docs, blog posts) for `0.16.4` before editing the
   Release, and note the result on #670.

## Acceptance mapping (#670)

- Tag/source mismatch and divergent history documented: yes (above).
- Users cannot mistake `v0.16.4` for a validated PyPI package: **not yet** - requires the owner to
  apply step 2 to the live Release.
- No force-moved tags, invented distributions or lost audit history: yes (read-only).
